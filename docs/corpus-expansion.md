# 语料扩展：从 4.2% 到 36%

> 本文记录 2026-11-19 那次扩采，以及扩采过程中量化出来的**采样偏差**。
> 这些数字要进最终报告 —— 它们是「我们的数据能不能代表 B站 评论区」这个问题的正面回答。

## 一、原来有多少，为什么不够

扩采之前，7 个视频的语料是这样的：

| 视频 | 真实评论数 | 我们有的是 | 覆盖率 |
|---|---:|---:|---:|
| 大肥鱼 | 1,301 | 280 | 21.6% |
| 晓艳天气预报 | 4,293 | 160 | 3.7% |
| 海龟汤（2） | 5,325 | 160 | 3.0% |
| 方的鸡 | 4,577 | 160 | 3.5% |
| 下饭 | 8,050 | 160 | 2.0% |
| Claude 实测 | 1,580 | 88 | 5.6% |
| 接B站 | 134 | 45 | 33.6% |
| **合计** | **25,260** | **1,053** | **4.2%** |

**4.2% 的采样率，是这份工作最初最大的软肋。** 而且那 4.2% 不是随机取的 ——
早期采集脚本的 `--max-comments 160` 是按**热度**取的，等于只保留了高赞评论。

## 二、扩采之后

用 `tools/deep_fetch.py` 按热度序深挖，每视频最多 100 页（B站 接口每页上限 20 条）：

| 视频 | 扩采后 | 覆盖率 |
|---|---:|---:|
| 大肥鱼 | 296 | 22.8% |
| Claude 实测 | 850 | 53.8% |
| 方的鸡 | 1,980 | 43.3% |
| 下饭 | 2,000 | 24.8% |
| 晓艳天气预报 | 2,000 | 46.6% |
| 海龟汤（2） | 1,985 | 37.3% |
| 接B站 | 56 | 41.8% |
| **合计** | **9,167** | **36.3%** |

**从 1,053 条到 9,167 条，8.7 倍。** 覆盖率从 4.2% 到 36.3%。

### 为什么没取全

B站 评论接口有个隐藏上限：`total` 字段（2 万、8 千那种数字）**包含二级回复和已删除的评论**，
顶层评论实际能翻到的页数远小于 `total / 20`。

实测同一个视频（下饭，`total` 标称 8,050）：

```
第   1 页 → 20 条
第 150 页 → 20 条
第 200 页 →  0 条      ← 到底了
第 300 页 → 请求失败
```

所以「拿到全部」在这个接口上做不到，**36.3% 已经接近天花板**。
这个限制本身值得写进报告的 limitations —— 它说明任何基于 B站 评论的研究都有同样的天花板。

## 三、量化出来的采样偏差

同时采了**热度序**（`sort=hot`）和**时间序**（`sort=time`）两份，
对照就能量化「只看高赞」到底偏了多少：

| 指标 | 热度序 | 时间序 | 差异 |
|---|---:|---:|---|
| 条数 | 9,167 | 1,496 | — |
| 平均点赞 | **49.1** | **6.2** | **7.9 倍** |
| 中位点赞 | 0 | 0 | — |
| p90 点赞 | 4 | 2 | 2.0 倍 |
| 零赞占比 | **55.1%** | **77.7%** | — |
| 表情率 | 22.0% | 15.0% | +7 pp |
| 平均字数 | **23.1** | **28.8** | 短 20% |

### 三条结论

**① 热度序把点赞放大了 7.9 倍。**
用「按热度取前 N」当训练数据，等于教模型「评论都该是有人点赞的」，
而实际上四分之三的评论**一条赞都没有**。

**② 高赞评论更短、表情更多。**
23.1 字 vs 28.8 字，表情率 22% vs 15%。
就是说热度序偏好的是「短平快、有梗、能秒懂」的评论 ——
这恰好是**最不像普通用户随手一写**的那一类。
拿它当「真人评论长什么样」的样本，会系统性高估「梗度」。

**③ 中位点赞两份都是 0。**
说明点赞分布极度长尾：绝大多数评论无人问津，极少数吸走全部注意力。
任何基于点赞的监督信号（比如我们后面要做的推荐/排序方向）
都必须先做 `log(1+like)` 或转成 top-20% 二分类，**不能直接回归**。

## 四、这一步对下游的影响

| 下游 | 变化 |
|---|---|
| 分类器训练集 | 1,053 → 6,997 条（清洗去重后） |
| 生成任务训练集 | 2,069 → 6,977 条 |
| 每视频样本量 | 88~280 → 296~2,000 |
| 采样偏差 | 「只看高赞」→ 仍有偏差，但已量化并可对照 |

**「仍有偏差」这句要诚实说**：扩采用的还是热度序，
只是为了做对照才采了 1,496 条时间序。
正式训练集如果要做「无偏」，应该改用时间序为主 —— 这一版没做，是已知的下一步。

## 五、怎么复现

```powershell
# 深采（断点续爬，可反复跑到预算用完）
python tools\deep_fetch.py --sort hot  --max-pages 100 --budget 400
python tools\deep_fetch.py --sort time --max-pages 12  --budget 90

# 合并成 jsonl
python tools\deep_fetch.py --merge-only --sort hot
python tools\deep_fetch.py --merge-only --sort time

# 重建数据集（会自动读取 data/deep/）
python tools\build_dataset.py --with-summary --strip-reply-prefix --out data\ds_v3
```

产物（均已 gitignore，含用户名，不入库）：

```

data/deep/<BV>-time.jsonl      时间序，1496 条
data/deep/<BV>-hot/p*.json     原始分页（断点续爬用）
data/ds_v3/sft_train.jsonl     训练集 6977 条
```

## 六、踩过的两个坑

**① 孤立代理字符**

B站 返回的评论里 emoji 有时被截成半个（`\ud83d` 单独出现），
`json.loads` 能解析成 str，但往 UTF-8 文件写会抛：

```
UnicodeEncodeError: 'utf-8' codec can't encode character '\ud83d': surrogates not allowed
```

解法：分页落盘用 `ensure_ascii=True`（转成 `\uXXXX` 永远合法），
合并时对文本再做一次 `s.encode('utf-8','replace').decode('utf-8')`。

**② Python 写不了工作区外面**

见 [ENVIRONMENT.md](ENVIRONMENT.md) 的坑 5。
深采脚本调用插件 CLI，必须给它一个指向工作区内的假 home。
